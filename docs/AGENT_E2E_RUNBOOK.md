# AGENT_E2E_RUNBOOK.md — прогон TUI/GUI агентом (ComputerUse)

Процедура для AI-агента: как самому выполнить DoD-пункт «прогон пользовательского
сценария» из `AGENTS.md` для задач, меняющих TUI/GUI, если харнес агента умеет
управлять десктопом. Пилотный прогон — issue #412 / PR #446.

## Когда это применимо

- **Харнес умеет управлять десктопом** (субагент ComputerUse или аналог:
  скриншоты, клики, клавиатура) → прогоняй сценарий сам по этой процедуре и
  приложи к PR факты: что запускал, что делал, что получилось.
- **Не умеет** (headless, только shell/файлы) → как раньше: юнит-тесты и пометка
  «требует ручной проверки» в PR; не выдавай `cargo test` за прогон.
- CI-раннеры headless: desktop-автоматизация — шаг харнеса, а не CI. Быстрые
  регрессии в CI остаются headless (ratatui `TestBackend`, egui `egui_kittest`);
  прогон их не заменяет, и они не заменяют прогон.

## Шаг 1. Изоляция реальных данных

Каталог данных (`dirs::data_dir()`): Windows `%APPDATA%\filar\`, macOS
`~/Library/Application Support/filar/`: `config.toml`, `settings.json`,
`pending_launch.json`, `sessions/`, `logs/`.

- Предпочтительно не трогать их вовсе: `FILAR_CONFIG` указывает на scratch-конфиг
  (первый приоритет загрузки, `crates/core/src/config.rs`).
- Если сценарий требует именно app-data лаунчера (как в #412) — сначала бэкап:
  скопировать файлы в `$env:TEMP\filarNNN-backup\` и запомнить SHA256
  (`Get-FileHash -Algorithm SHA256`). После прогона восстановить и сверить хеши;
  факт «хеши совпали» — в описание PR.
- `pending_launch.json` после запуска TUI потребляется и удаляется — его тоже
  бэкапить.
- Никогда не гоняй лаунчерный сценарий против реального конфига без бэкапа.

## Шаг 2. Сборка и запуск окон

- `cargo build` (debug достаточно). Бинарник: `target\debug\filar.exe`.
- GUI-лаунчер: `Start-Process .\target\debug\filar.exe -ArgumentList "--gui-only"`
  → отдельное окно «Filar - Launcher».
- TUI: `Start-Process .\target\debug\filar.exe` → отдельное консольное окно.
- **Не используй IDE-встроенный терминал**: синтетические клики не фокусируют
  IDE, а горячие клавиши перехватывает редактор (Ctrl+O = «open file», Ctrl+Q
  оставляет процесс-сироту). Отдельное окно ОС обязательно.

## Шаг 3. Управление через ComputerUse

- Фокус: первый клик по неактивному окну только активирует его; чтобы ввод
  клавиш дошёл до приложения, кликни ещё раз.
- DPI: координаты кликов — в физических пикселях; при масштабе 150% умножать
  логические координаты на 1.5 (или helper через Win32 `GetDpiForMonitor`).
  Helper-скрипт после прогона удалить.
- Скриншоты складывать в `$env:TEMP`, не в репозиторий; путь возвращать так,
  чтобы главный агент прочитал файл как изображение и сверил состояние глазами.
- Ориентиры filar: заголовок «Filar - Launcher»; оверлей `Select host (Ctrl+O)`;
  `Esc` закрывает оверлеи; `Ctrl+Q` — выход из TUI.
- Прогон не ослабляет гейт подтверждений: агент нажимает настоящие Approve в UI,
  а не обходит его.

## Шаг 4. Верификация: экран + артефакты

Скриншот — подсказка, а не доказательство. Сверяй наблюдения с
машинно-проверяемым:

- `pending_launch.json` перезаписан и содержит ожидаемые `ssh_targets` (имена,
  хосты, типы auth); ключа `"password"` в нём быть не должно (#255);
- лаунчер завершился после Launch; после `Ctrl+Q` процессов filar не осталось
  (`Get-Process filar`);
- хеши восстановленных файлов совпадают с исходными;
- при расхождениях — логи в `<app-data>\logs\`.

## Шаг 5. Уборка (обязательна)

- Убить оставшиеся процессы filar.
- Восстановить бэкапы, сверить SHA256.
- Удалить helper-скрипты, скриншоты, temp-каталоги прогона.
- Коммит — только явные пути (`git add <файлы>`), никогда `git add -A` /
  стейджинг вайлдкардом: артефакты прогона не должны попасть в историю.
  Некоторые IDE пересоздают удалённые PNG, пока на них ссылаются в чате, —
  чистить в самом конце сессии.

## Чек-лист для описания PR

- [ ] `cargo build --workspace` / `cargo test --workspace` зелёные;
- [ ] сценарий из issue прогнан: что запускалось, что делалось, что получилось;
- [ ] артефакты прогона (имена в `pending_launch.json`, скриншот, хеши);
- [ ] данные пользователя не пострадали: не затрагивались / восстановлены;
- [ ] если прогон невозможен — причина прямо в PR.

## Ограничения

- Нужен активный (не заблокированный) десктоп; автоматизация чувствительна к
  фокусу и DPI.
- Если сценарию нужно настоящее SSH-подключение, используй свой тестовый хост
  (например docker-sshd: Ubuntu 22.04 + openssh-server, `docker/sshd`); инвариант
  zero-install действует и в прогоне.

## Пример: #412 (Windows)

Ручная `[[ssh_targets]]`-запись `fleet-manual-01` в app-data `config.toml` →
`filar --gui-only` → клик Launch → `pending_launch.json` = запись лаунчера +
ручная (дубликат по имени отброшен) → отдельная консоль → Ctrl+O: `local`,
`VPS DE`, `fleet-manual-01` (скриншот) → Esc → Ctrl+Q → конфиги восстановлены,
хеши совпали. Подробнее — `PROGRESS.md`, раздел «Issue #412».

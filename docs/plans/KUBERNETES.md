# Kubernetes в filar: под как цель, флот по селектору

> Дизайн-документ эпика #559. Этап 1 — веха 2.1.0, этап 2 — веха 2.2.0,
> этап 3 — бэклог. Задачи ссылаются сюда за контекстом; при расхождении
> побеждает тело issue, а документ правится в том же PR.

## 1. Зачем

Сервер всё чаще — не хост, а под. Админ, который ведёт хосты через filar,
сегодня уходит в `kubectl exec`, теряя всё, ради чего существует filar:
подтверждение каждой команды, арбитр, оценку безопасности, ранбуки, флот.
Цель — чтобы под стал такой же целью вкладки, как SSH-хост, а группа подов по
label selector — таким же флотом, как группа хостов по тегам.

## 2. Ключевая идея: это ещё один `CommandExecutor`

Агент, гейт, арбитр, оценка, история, экспорт работают поверх
`CommandExecutor` и о транспорте не знают. Kubernetes — новая реализация
трейта, **контракт трейта не меняется** (инвариант 4).

Проверено прототипом на k3s v1.33 и `kube` 4.2 (WebSocket exec):

| Что | Результат |
|---|---|
| Один `exec` с `stdin=true, tty=false` держит живой `sh` | да: `cd`, `export` сохраняются между командами |
| Маркерный протокол как у SSH (`printf '\n<tag>__%d__%s__\n' "$?" "$PWD"`) | работает без изменений: код возврата и `PWD` |
| stdout и stderr — раздельные потоки | да; stderr может прийти чуть позже маркера → нужен тот же «добор» stderr, что в SSH |
| `$$` шелла для прерывания | доступен (`printf … "$$"`) |
| Задержка | 3 команды ≈ 75 мс на локальном кластере |
| Список подов по селектору (`app=web`) | `Api::<Pod>::list` с `labels(...)` |

Отсюда архитектура:

```
            ┌────────────── filar-transport ──────────────┐
            │  shell_protocol (общий, вынесен из ssh.rs)  │
            │  маркер, разбор, добор stderr, ресинк,      │
            │  read_shell_pid, interrupt_command          │
            │        ▲                         ▲          │
            │  SshExecutor (russh канал)  KubeExecutor    │
            │                             (exec WebSocket)│
            └─────────────────────────────────────────────┘
```

## 3. Инварианты

1. **Zero-install.** `exec` использует шелл, который уже есть в контейнере;
   ничего не пишется и не ставится. **Открытый вопрос — distroless.** В
   контейнере без шелла работать нечем. Стандартный выход — эфемерный
   debug-контейнер (`kubectl debug`), но это артефакт в кластере: запись в
   `spec.ephemeralContainers`, которая живёт до пересоздания пода. Этап 1 его
   **не делает**: «в контейнере нет /bin/sh» — понятная ошибка. Решение
   (отдельное исключение в AGENTS.md по образцу #531 или отказ) — за
   мейнтейнером.
2. **Подтверждение.** Гейт не меняется: команды в поде проходят тот же
   `check_command`. Новое — **контекст в окне подтверждения**: «prod / shop /
   web-7f9c… / main» должно быть видно до Approve, как радиус флота.
3. **Секреты.** Доступ к кластеру — из kubeconfig пользователя: сертификаты,
   токены, exec-плагины (`aws eks get-token`, `gke-gcloud-auth-plugin`,
   `kubelogin`). Это аналог файла SSH-ключа: filar **читает** его и никогда
   не копирует содержимое в `config.toml`, `pending_launch.json`, логи и
   ошибки. В конфиге — только путь к kubeconfig и имя контекста.
4. **Изоляция.** Вся специфика `kube`/`k8s-openapi` — внутри
   `filar-transport` за фичей `kube`. Агент видит лишь `CommandExecutor` и
   текстовое описание цели.
5. **Без посредников.** Трафик идёт напрямую на API-сервер кластера —
   туда же, куда ходит `kubectl`. Прокси из kubeconfig (`proxy-url`) и
   окружения поддерживаются (фичи `http-proxy`, `socks5`): у корпоративных
   пользователей они есть.

## 4. Цель: что такое «под» в конфиге

Поды эфемерны: имя `web-7f9c6d-xk2p` меняется при каждом раскатывании.
Поэтому цель хранит **как найти** под, а не его имя:

```toml
[[kube_targets]]
name = "shop-web"                  # имя цели — как у [[ssh_targets]]
context = "prod-eu"                # ОБЯЗАТЕЛЬНО: никакого current-context
namespace = "shop"
selector = "app=web"               # или pod = "web-7f9c6d-xk2p" — точное имя
container = "main"                 # необязательно; по умолчанию — единственный / по аннотации default-container
kubeconfig = "~/.kube/config"      # необязательно; по умолчанию $KUBECONFIG / ~/.kube/config
shell = "/bin/sh"                  # необязательно
tags = ["prod", "k8s"]
```

- **Контекст обязателен.** `current-context` — классическая ловушка: кто-то
  переключил его в соседнем терминале, и команда ушла в прод. filar его не
  использует никогда.
- **Выбор пода по селектору:** только `Running` + `Ready`, сортировка по
  имени, берётся первый. Если подходящих несколько, это видно в статус-баре
  (`web ×3 → web-7f9c…`); выбрать другой можно в Ctrl+O.
- **Пересоздание пода.** Если `exec` оборвался, а пода больше нет,
  переподключение находит новый под по тому же селектору. Об этом
  **обязательно** говорится в ленте: «Под web-7f9c… пропал, вкладка теперь в
  web-a1b2… — состояние шелла (cd, переменные) потеряно». Тихая смена пода —
  баг: агент рассчитывает на персистентность шелла.
- **Теги** работают как у SSH: политики `[[tag_policies]]`, read-only группы
  и оценка безопасности (теги уходят в описание цели).

## 5. `KubeExecutor`

- `connect(target, kubeconfig_provider)`: загрузить kubeconfig с явным
  контекстом → `Client` → выбрать под → `exec [shell]` с
  `stdin/stdout/stderr`, без TTY → задача-читатель превращает stdout и stderr
  в те же `ChannelEvent`, что у SSH → `read_shell_pid`.
- `run`: общий маркерный протокол (`shell_protocol::recv_until_marker`).
  Таймаут → прерывание → ресинк, как в SSH.
- `cancel`: второй `exec` на тот же под с
  `shell_protocol::interrupt_command(pid)` (`ps`/`awk`/`kill`). Если в
  контейнере нет `ps` (минимальный образ), закрыть exec-поток (шелл умрёт
  вместе с детьми) и честно сообщить: «прервано пересозданием шелла, cd и
  переменные сброшены». Прерывание не должно молча «не сработать»
  (AGENTS.md: отмена обязана проходить).
- `set_cwd`/`current_cwd`: как у SSH (маркер отдаёт `$PWD`).
- Ошибки: «нет такого контекста», «под не Ready», «в контейнере нет
  /bin/sh», «API-сервер недоступен». Каждая — с контекстом и namespace, без
  токенов и сертификатов.
- **Отказ доступа (403) — две разные причины**, и сообщение называет нужную:
  - RBAC: нет права `create` на `pods/exec` (или `get`/`list` на `pods` для
    селектора) — «нет права create на pods/exec в namespace shop (контекст
    prod-eu)». Во многих компаниях exec в прод запрещён — это нормально,
    filar его не обходит.
  - Политика допуска (Kyverno, OPA Gatekeeper, Pod Security Admission,
    webhook) — текст политики показывается как есть: обычно там написано,
    почему нельзя.
- **Ограничения пода** (`PodLimits`) читаются из спецификации того же пода —
  новых прав не нужно, в контейнере ничего не запускается: лимиты и requests
  памяти/CPU контейнера, `runAsUser` / `runAsNonRoot`, `readOnlyRootFilesystem`,
  отброшенные capabilities. Они уходят агенту (§6) и в статус вкладки (§7).

**Чего exec не боится и чего стоит бояться:**

- **Нет места на диске.** Сам exec места не требует: шелл запускается из
  образа, filar пишет команды в stdin, временных файлов нет. Войти в под с
  забитым диском можно; падают только пишущие команды — а `du`/`df` и есть
  то, зачем туда идут. `readOnlyRootFilesystem` — то же самое: читать можно,
  писать только в смонтированные тома. (Эфемерный debug-контейнер, наоборот,
  при `DiskPressure` ноды не поднимется — его образ надо скачать.)
- **Память — главная ловушка, которой нет у SSH.** Процессы из exec
  считаются в лимит памяти (и pids) того же контейнера. Тяжёлая команда у
  приложения, работающего у потолка, вызывает OOM, а OOM-killer нередко
  убивает процесс приложения — под перезапускается, диагностика уронила
  сервис. Поэтому лимит виден агенту и человеку, а промпт требует лёгких
  команд.
- **Пользователь контейнера** — в проде обычно не root (у distroless uid
  65532): нет `sudo`, часть файлов не читается, часть capabilities отброшена
  (`ping` без `NET_RAW`). Прерывание filar работает: `kill` своих процессов
  разрешён.
- **Аудит.** Многие кластеры пишут каждый exec в журнал аудита — действия
  через filar там видны.
- Keepalive: WebSocket ping. Обрыв до отправки команды → один тихий
  реконнект, как `auto_reconnect` у SSH; обрыв после — никогда не повторять
  автоматически.

**Зависимости:** `kube` 4.x (`client`, `config`, `ws`, `rustls-tls`, `ring` —
провайдер crypto тот же, что у остального воркспейса; `http-proxy`,
`socks5`), `k8s-openapi` с фичей версии API. MSRV `kube` 4.2 — 1.89, у нас
1.99. Всё под фичей `kube` в `filar-transport`: включена в приложении,
выключаема для встраивания (бот, мобилка).

## 6. Агент

- Системный промпт для пода — отдельная ветка `build_system_prompt` (рядом с
  local/SSH/Windows): «Ты внутри контейнера C пода P (namespace N, контекст
  X). Файловая система контейнера эфемерна — изменения пропадут при
  пересоздании пода. Не ставь пакеты. `kubectl` внутри контейнера, скорее
  всего, нет и прав на API тоже. Минимальный образ: многих утилит может не
  быть — проверяй `command -v`». Правка промпта → прогон `eval-smoke`
  (AGENTS.md), плюс 2–3 кейса «под» в датасет.
- **Ограничения пода в промпте** — фактами из `PodLimits` (неизвестное не
  упоминается) и правило: «твои процессы делят лимит памяти с приложением;
  OOM может убить приложение — избегай тяжёлых команд (`find /` по большому
  дереву, чтение больших файлов целиком, сортировка больших логов),
  ограничивай вывод, смотри размер до чтения». Для не-root — `sudo`, скорее
  всего, нет; для read-only ФС — писать только в смонтированные тома.
- Описание цели для арбитра и оценки безопасности:
  `Kubernetes pod shop/web-7f9c… (container main, context prod-eu, tags: prod, k8s; non-root, read-only fs, memory limit 512Mi)`.
  Тег `prod` и маленький лимит памяти заметно влияют на оценку Jev — это и
  нужно.

## 7. TUI и лаунчер

- **Ctrl+O:** в общем списке рядом с SSH-хостами — kube-цели (`⎈ shop-web`).
  Фильтр и теги работают как сейчас.
- **Статус-бар:** `⎈ prod-eu › shop › web-7f9c… › main [prod]`; длинные части
  сокращаются. ASCII-фоллбэк для conhost: `k8s:`. Следом — ограничения пода:
  `non-root · ro-fs · mem 512Mi`; полностью — в F1.
- **Отказ доступа** при подключении (RBAC или политика) — понятная строка в
  ленте, вкладка остаётся на прежней цели.
- **Окно подтверждения:** строка цели с контекстом. Контекст с тегом `prod`
  подсвечивается так же, как деструктивная команда.
- **Лаунчер:** тип цели «Kubernetes»: путь к kubeconfig (выбор файла),
  контекст — выпадающий список, прочитанный из kubeconfig **локально**, без
  сети; namespace, селектор или под, контейнер, теги. Кнопка «Check» по
  желанию делает один запрос к API (список подов) — это сеть, только по
  нажатию.
- **CLI:** `filar --target shop-web` работает для kube-цели так же, как для
  SSH.

## 9. Тестирование

- **Юнит:** общий протокол (уже покрыт тестами SSH — переезжает вместе с
  ними), выбор пода из списка (Ready, сортировка), разбор `[[kube_targets]]`,
  описание цели, промпт.
- **Интеграционные `#[ignore]`** против кластера — по образцу docker-sshd:
  `docker/k3s/README.md` с инструкцией (k3s в Docker или kind) и манифестом
  тестового деплоймента (`app=web`, 3 реплики, два контейнера, образ с
  busybox). Покрывают: персистентность шелла, коды возврата, stderr, cancel,
  удаление пода → реконнект с уведомлением, отказ RBAC, контейнер без шелла.

- **CI:** юнит-тесты как обычно. Интеграция в CI — отдельным решением
  (kind в GitHub Actions — ~1–2 мин на подъём).

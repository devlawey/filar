# Kubernetes и логи в filar

> Дизайн-документ трёх вех: **3.0.0** — read-only API кластера и флот поверх
> API, **3.0.1** — работа внутри пода, **3.0.2** — работа с логами. Задачи
> ссылаются сюда за контекстом; при расхождении побеждает тело issue, а
> документ правится в том же PR.

## 1. Подход: API прежде всего

Сервер всё чаще — не хост, а под, и в нём действуют другие правила:

- **В контейнеры обычно не заходят.** Большая часть прод-подов собрана из
  distroless-образов или `FROM scratch`: в них нет шелла, нет `ls`, нет `ps`.
  Диагностика идёт через API кластера (статус пода и причины рестартов,
  события, `kubectl logs`, в том числе `--previous` упавшего запуска) и через
  централизованное хранилище логов.
- **Логи — не файл на сервере.** Приложение пишет в stdout/stderr, kubelet
  складывает это на ноду, сборщик-DaemonSet (vlagent, Fluent Bit, Vector,
  Alloy/Promtail, Filebeat) отправляет в хранилище (VictoriaLogs,
  OpenSearch/Elasticsearch, Loki, облачные), а хранилище опрашивают по HTTP
  API. На лог-сервер по SSH не ходят.
- **Exec — инструмент, а не основа.** Если шелл есть, войти в под удобно. Если
  нет — эфемерный debug-контейнер, по явному действию человека.

Отсюда три вехи — от безопасного и всегда работающего к точечному:

| Веха | Что | Шелл в поде нужен? | Пишет в кластер? |
|---|---|---|---|
| 3.0.0 | Read-only API кластера, вкладка кластера, флот поверх API | нет | нет |
| 3.0.1 | Exec-шелл в под, Ctrl+T, HTTP-диагностика через port-forward, эфемерный debug-контейнер | да / нет для port-forward и debug | только debug-контейнер, по явному действию |
| 3.0.2 | Источники логов: VictoriaLogs, OpenSearch/Elasticsearch, Loki; связка с подами и флотом | нет | нет |

filar — универсальный инструмент: никакого «нашего» стека не подразумевается,
каждый тип хранилища логов — адаптер за общим трейтом.

## 2. Инварианты

1. **Zero-install.** API-вызовы, exec и port-forward ничего не пишут ни в
   под, ни в кластер. Единственное исключение — **эфемерный debug-контейнер**
   (#576): запись в `spec.ephemeralContainers` остаётся до пересоздания пода.
   Оформляется исключением в AGENTS.md по образцу #531: только по явному
   действию пользователя, образ из разрешённого списка, окно подтверждения с
   текстом о следе, права не шире целевого контейнера, агент не инициирует,
   след фиксируется в сессии. `kubectl debug --copy-to` и `debug node/…` не
   делаются.
2. **Подтверждение.** Команды в поде проходят тот же `check_command`.
   Чтение через API, port-forward и запросы к логам — read-only класс:
   подтверждение в `always`/`explain`, без него в `allowlist`/`never`;
   политики тегов только ужесточают. Флот — один вопрос подтверждается один
   раз с радиусом, в любом режиме. В окне подтверждения видна цель:
   «prod-eu / shop / web-7f9c… / main».
3. **Секреты.**
   - Доступ к кластеру — из kubeconfig пользователя (сертификаты, токены,
     exec-плагины `aws eks get-token`, `gke-gcloud-auth-plugin`,
     `kubelogin`): filar его читает и никогда не копирует в `config.toml`,
     `pending_launch.json`, логи и ошибки.
   - Ключи хранилищ логов — в env/keyring под `key_env`, как у LLM-профилей.
   - Объект `Secret` не читается никогда; значения env, last-applied,
     похожие на секрет значения ConfigMap, пароли в аргументах и в логах
     маскируются перед моделью (#573).
4. **Изоляция.** `kube-rs` — внутри `filar-transport` за фичей `kube`; агент
   видит трейты `ClusterApi` (#572), `CommandExecutor` (#563),
   `LogSource` (#579) и текстовые описания целей.
5. **Без посредников.** Трафик идёт напрямую на API-сервер кластера и в
   хранилище логов пользователя. Прокси из kubeconfig и окружения
   поддерживаются (фичи `kube`: `http-proxy`, `socks5`).

## 3. Цели и конфигурация

Цель Kubernetes-вкладки — **кластер** (контекст kubeconfig) с namespace;
поды эфемерны (`web-7f9c6d-xk2p` меняется при каждом раскатывании) и
выбираются внутри кластера.

```toml
[[kube_clusters]]                   # #562
name = "prod-eu"
context = "prod-eu"                 # ОБЯЗАТЕЛЬНО: current-context не используется никогда
kubeconfig = "~/.kube/config"       # необязательно; $KUBECONFIG, затем ~/.kube/config
namespaces = ["shop", "pay"]        # необязательно; нужно при RBAC на уровне namespace
default_namespace = "shop"
tags = ["prod", "k8s"]
debug_images = ["busybox:1.37"]     # #576; пусто — debug-контейнеры недоступны
diagnostic_ports = [8080, 6060]     # #578

[[host_groups]]                     # #568
name = "web-prod"
kube = { clusters = ["prod-eu", "prod-us"], namespace = "shop", selector = "app=web" }

[[log_sources]]                     # #579
name = "vlogs-prod"
kind = "victorialogs"               # victorialogs | opensearch | elasticsearch | loki
url = "https://vlogs.example.com"
auth = "bearer"
key_env = "FILAR_LOGS_VLOGS_PROD"
clusters = ["prod-eu"]
max_window_hours = 24
max_lines = 500
```

- **Контекст обязателен.** `current-context` — классическая ловушка: его
  переключили в соседнем терминале, и команда ушла в прод.
- Имена кластеров и SSH-целей — одно пространство (`--target`, Ctrl+O).
- Теги кластера работают как у SSH: политики, оценка безопасности.

## 4. Веха 3.0.0 — API кластера и флот

**`ClusterApi`** (#572) — read-only трейт в `filar-transport` поверх
`kube-rs`: поды (фаза, Ready, рестарты, причина последнего завершения —
`OOMKilled`, код), события, логи (`previous`, `since`, `tail`, лимит байт),
workloads, история раскаток, ноды, `top` через `metrics.k8s.io`
(`Unsupported`, если metrics-server нет), сервисы, endpoints, ingress,
ConfigMap'ы. Методов записи нет, `Secret` не запрашивается. Списки
ограничены, ошибки 403 различают RBAC («нет права list на pods в
namespace shop») и политику допуска (текст как есть).

**Инструменты агента** (#574): `k8s_get`, `k8s_describe` (сводка + события),
`k8s_logs`, `k8s_events`, `k8s_top`, `k8s_rollout_history` — компактные
таблицы через препроцессоры, всё через редакцию (#573). Промпт вкладки
кластера: «сначала статус, события, логи и `--previous`; изменять кластер ты
не можешь; Secret недоступны».

**Вкладка кластера** (#575): Ctrl+O → кластер → namespace; статус-бар
`⎈ prod-eu › shop [prod]`; вызовы API — блоками в ленте, как команды.

**Флот поверх API** (#567, #568, #569). Цель члена флота — перечисление
`FleetTarget::{Ssh, KubePod, KubeCluster}`. Группа по `kube`:

- с `selector` — члены флота = готовые поды во всех указанных кластерах на
  момент входа (состав заморожен, как у SSH-флота);
- без `selector` — члены = сами кластеры/namespace («как выглядит деплоймент
  web в prod-eu и prod-us»).

Агент вызывает read-only инструмент — filar раздаёт вызов членам
(`max_parallel`), ответы проходят редакцию и складываются существующим fold в
таблицу различий; сырые ответы модель не видит. Исходы: ответ, нет ответа,
отказ доступа, **под исчез**. Шелл не нужен — флот работает и с distroless.

## 5. Веха 3.0.1 — внутри пода

### Exec-шелл (#561, #563, #564, #565)

`KubeExecutor` — ещё одна реализация `CommandExecutor`, **контракт трейта не
меняется**. Проверено прототипом на k3s v1.33 + `kube` 4.2 (WebSocket exec):

| Что | Результат |
|---|---|
| Один `exec` с `stdin=true, tty=false` держит живой `sh` | `cd`, `export` сохраняются между командами |
| Маркерный протокол SSH (`printf '\n<tag>__%d__%s__\n' "$?" "$PWD"`) | работает без изменений |
| stdout и stderr | раздельны; stderr может прийти после маркера — нужен «добор», как в SSH |
| `$$` шелла для прерывания | доступен |
| Задержка | 3 команды ≈ 75 мс на локальном кластере |

```
            ┌────────────── filar-transport ──────────────┐
            │  shell_protocol (общий, вынесен из ssh.rs)  │  ← #561
            │  маркер, разбор, добор stderr, ресинк,      │
            │  read_shell_pid, interrupt_command          │
            │        ▲                         ▲          │
            │  SshExecutor (russh канал)  KubeExecutor    │  ← #563
            │                             (exec WebSocket)│
            └─────────────────────────────────────────────┘
```

- Под задаётся `PodRef { cluster, namespace, pod | selector, container }`;
  по селектору — `Running`+`Ready`, по имени, первый. Вход — из вкладки
  кластера (новая вкладка пода) или `--target prod-eu/shop/web-…`.
- `cancel` — второй `exec` с `interrupt_command(pid)`; нет `ps` — шелл
  пересоздаётся с честным сообщением. Отмена не должна молча не сработать.
- **Пересоздание пода** — реконнект в новый под по селектору и обязательная
  строка в ленте: «под web-7f9c… пропал, вкладка теперь в web-a1b2… — cd и
  переменные сброшены». Тихая смена — баг.
- **Отказы** 403: RBAC (`create` на `pods/exec`) и политика — разные
  сообщения, без обхода.

**Чего exec не боится и чего стоит бояться:**

- **Нет места на диске.** Сам exec места не требует: шелл из образа,
  команды — через stdin, временных файлов нет. Падают только пишущие команды,
  а `du`/`df` и есть то, зачем заходят. `readOnlyRootFilesystem` — то же.
- **Память — главная ловушка, которой нет у SSH.** Процессы из exec
  считаются в лимит памяти (и pids) того же контейнера; OOM у приложения,
  работающего у потолка, может убить процесс приложения — диагностика
  уронила сервис. Поэтому `PodLimits` (лимиты, пользователь, read-only ФС,
  capabilities — из спецификации пода, без новых прав) видны агенту (#564) и
  в статус-баре (#565), а промпт требует лёгких команд.
- **Пользователь контейнера** обычно не root: нет `sudo`, часть файлов и
  capabilities недоступны. Прерывание filar работает — `kill` своих процессов
  разрешён.
- **Аудит.** Многие кластеры пишут каждый exec в журнал аудита — действия
  через filar там видны.

### Ctrl+T в под (#577)

Второй `exec` с TTY, resize-канал, Ctrl+C байтом. Независим от шелла агента.

### HTTP-диагностика через port-forward (#578)

Инструмент `pod_http_get`: только `GET` к объявленным или разрешённым портам
(`/metrics`, `/healthz`, `/debug/pprof/…?debug=1`), туннель внутри процесса,
ответ ≤ 1 МБ. Путь для distroless без следа в кластере.

### Эфемерный debug-контейнер (#576)

Для подов без шелла. Только явное действие человека; образ из
`debug_images`; окно подтверждения: «в под X будет добавлен эфемерный
контейнер Y; он останется в спецификации пода до его пересоздания».
`targetContainerName` — общее пространство процессов, файлы приложения через
`/proc/<pid>/root/…` (pid filar находит и даёт агенту). `securityContext` не
шире целевого контейнера. Нужно право `patch` на `pods/ephemeralcontainers`;
политики (PSA/Kyverno) часто запрещают — понятный отказ. Образ скачивается на
ноду: при `DiskPressure` не поднимется.

## 6. Веха 3.0.2 — логи

**`LogSource`** (#579) — трейт по образцу `RiskScorer`: запрос на языке
источника + окно + лимит → строки. Рамки ставит filar, а не модель: окно
≤ `max_window_hours` (без окна запрос не уходит), строк ≤ `max_lines`,
таймаут, отмена закрывает соединение. Неосторожный запрос за неделю может
положить лог-сервер — это та же «тяжёлая команда». Только эндпоинты поиска.

Инструмент `query_logs` доступен в любой вкладке; вывод **сворачивается**
(одинаковые сообщения после нормализации чисел/uuid/времени — группа со
счётчиком и распределением по времени) и проходит редакцию.

| Адаптер | Запрос | Особенности |
|---|---|---|
| VictoriaLogs (#580) | `POST /select/logsql/query` (LogsQL), JSON-строки `_msg/_time/_stream` | тенант — заголовки `AccountID`/`ProjectID`; auth через прокси (vmauth): basic/bearer; закрытие соединения останавливает запрос; поля vlagent `kubernetes.pod_name`, `kubernetes.pod_namespace`, `kubernetes.container_name` |
| OpenSearch / Elasticsearch (#581) | `POST /{index}/_search`: `range` по времени + `query_string` или DSL | basic / ApiKey / bearer, свой CA; поля Fluent Bit и Filebeat — пресеты |
| Loki (#582) | `GET /loki/api/v1/query_range` (LogQL) | `X-Scope-OrgID`; `streams` и `matrix` |

**Связка с Kubernetes** (#583): источник связан с кластерами; по пресету полей
(`k8s_fields`) filar сам строит запрос «логи этого пода/группы за окно» —
`pod_logs_history`. Отличие от `k8s_logs`: тот — короткий хвост с ноды без
истории, этот — история из хранилища, включая удалённые поды. Для флота —
один запрос на всю группу, свёртка по подам.

**UI** (#584): источники в лаунчере (ключ в keyring, Check), блок логов в
ленте со свёрнутым и раскрытым видом.

## 7. Тестирование

- **Юнит** — в каждой задаче; HTTP-адаптеры — на mock-сервере.
- **Интеграционные `#[ignore]`** против `docker/k8s` (#571): kind или k3s в
  Docker; манифесты `web` (3 реплики, два контейнера, ограничения пода, логи
  в stdout), `crashy` (для `--previous`), `distroless`, ServiceAccount'ы
  `reader` и `no-exec`. В окружении агента k3s поднимается на Docker с
  обёрткой runc (VM запрещает отрицательный `oom_score_adj`), airgap-образами
  и локально собранным busybox (Docker Hub недоступен).
- **Хранилища логов**: VictoriaLogs и Loki — одиночные бинарники из GitHub
  Releases; OpenSearch/Elasticsearch — mock с записанными ответами и ручной
  пункт в SMOKE.
- **DoD с бинарником** — TUI в tmux против тестового кластера, как для #551.

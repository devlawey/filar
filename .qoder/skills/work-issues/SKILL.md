# work-issues

Автономно закрыть несколько issue репозитория `filar` подряд, без пауз и
вопросов пользователю. Предназначен для ночного прогона («я сплю — сделай всё
и остановись»).

**Аргумент:** номера issue через запятую и/или диапазон через дефис, например
`271-274`, `271,273`, `271-273,275`. Если аргумент не передан — остановиться и
спросить пользователя, какие issue обрабатывать.

## Вход

1. Разверни аргумент в упорядоченный список уникальных номеров issue
   (`271-274` → 271, 272, 273, 274). Обрабатывай строго по порядку, по одной.
2. `git pull` на актуальный `main`. Убедись, что рабочее дерево чистое и ты на
   `main`.

## Цикл на каждую issue

Для каждой issue по порядку:

1. **Реализация.** Загрузи скилл `work-one-issue` и выполни его для номера.
   Он создаст ветку от `main`, реализует правку строго по телу issue, обновит
   `PROGRESS.md` и `CHANGELOG.md`, закоммитит, запушит и откроет PR с
   `Closes #N`. Запомни номер созданного PR.

2. **Ожидание ревью.** Подожди ~5 минут, пока проедут автоматические ревью
   (CodeRabbit, `ai-review`). Конкретно — `Start-Sleep -Seconds 300` в
   PowerShell. Перед чтением комментариев проверь статус check-run `review`:
   если он ещё `in_progress`, подожди дополнительно (у ai-review таймаут
   ~15 минут) и перепроверь.

3. **Обработка ревью.** Загрузи скилл `address-review` и выполни его для номера
   PR: прочитай все комментарии (сводку и инлайн), рассортируй на
   ПРИНЯТЬ / ОТКЛОНИТЬ / ВНЕ СКОПА, внеси справедливые правки в ту же ветку,
   закоммить, запушь, ответь в тредах и сверни их. Отклонённые комментируй с
   обоснованием — молча не игнорируй.

4. **Повтор.** Снова подожди ~5 минут и повтори шаг 3. Делай до 4 раундов
   `address-review` или до тех пор, пока PR не станет чистым (нет неразрешённых
   тредов и нет непринятых справедливых замечаний) — что раньше. Каждый новый
   push триггерит инкрементальный ai-review, поэтому после каждого раунда
   правок обязательно перечитывай комментарии.

5. **Мерж.** Когда PR чист — смержи его (метод `merge`, как принято в репо),
   удали удалённую ветку (`git push origin --delete <branch>`), удали локальную
   ветку (`git branch -d <branch>`), переключись на `main` и `git pull`.

6. Переходи к следующей issue.

## Финал

- После всех issue — дебаг-сборка: `cargo build --workspace`. Должна быть
  зелёной.
- Остановись. Дай сводку: какие issue закрыты, какие PR смержены, что требует
  ручной проверки (прогон бинарника/TUI/GUI по DoD), что отклонено/вынесено
  вовне.

## Полномочия (важно)

В рамках этого скилла агент действует автономно и **уполномочен**:
- мержить PR;
- удалять удалённые и локальные ветки;
- не останавливаться на ревью.

Это осознанное исключение: `work-one-issue` и `address-review` останавливаются
на ревью и не мержат, но здесь пользователь спит и явно разрешил доводить
каждую issue до мержа. Финальное слово по каждому отдельному замечанию всё
равно остаётся за здравым смыслом (см. ниже), а не за «закрыть любой ценой».

## Ограничения и правила

- Инварианты из AGENTS.md действуют всегда. Правку, задевающую священный
  инвариант, не вноси — остановись и зафиксируй проблему в сводке.
- Одна issue = одна ветка = один PR. Не смешивай несвязанные правки.
- Не принимай комментарии ревью слепо ради «ноль комментариев»: ложные
  срабатывания отклоняй с обоснованием и сворачивай тред.
- Если issue противоречива или критично неполна и требует решения человека —
  пропусти её, зафиксируй в сводке и перейди к следующей (не угадывай).
- Не тащи в PR посторонние изменения рабочего дерева (например, дрейф
  `Cargo.lock` от несвязанной зависимости) — откатывай их перед коммитом.
- Запрещён force-push и прямой push в `main` (кроме мержа PR).

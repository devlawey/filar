# Filar — Пользовательская инструкция

> Терминал с AI-агентом поверх SSH. Агент выполняет команды на локальной или
> удалённой машине, запрашивая подтверждение перед каждой операцией.

---

## 1. Быстрый старт

### 1.1. Запуск (основной способ)

1. Скачайте релизный бинарник или соберите из исходников (`cargo build --release`):
   - **Windows:** `filar.exe`
   - **macOS (Apple Silicon):** `filar-*-macos-aarch64` → `chmod +x` и при
     необходимости `xattr -d com.apple.quarantine …` (см. `docs/PLATFORM_NOTES.md`)
2. Запустите бинарник (двойной клик или из терминала)
3. Откроется GUI-лаунчер — введите модель, URL и API-ключ прямо в интерфейсе
4. Нажмите **Launch**

API-ключ сохранится в системном хранилище учётных данных автоматически —
**Windows Credential Manager** или **macOS Keychain** (service `filar`).
При следующем запуске поле уже будет заполнено. Пароли SSH сохраняются, если
отметить «Save password» для соответствующего SSH-профиля (ключ
`ssh_target:{alias|SSHn}`).

### 1.2. Запуск из терминала

```bash
# Windows (PowerShell) или macOS (Terminal / iTerm2)
filar          # Windows: filar.exe
```

Без аргументов — всегда открывается GUI-лаунчер.

### 1.3. CLI-режим (напрямую в TUI, без GUI)

CLI-режим читает `config.toml` (см. раздел 2). Нужны env-переменные для ключей.

```bash
# Локальная машина (требуется GLM_API_KEY в env)
export GLM_API_KEY="ваш-ключ"          # macOS / bash / zsh
# $env:GLM_API_KEY = "ваш-ключ"        # Windows PowerShell
filar --target local

# SSH-таргет + конкретный LLM-профиль
filar --target test-docker --llm glm

# Восстановить предыдущую сессию
filar --target local --session 1718900000
```

### 1.4. Сборка из исходников

```bash
git clone https://github.com/devlawey/filar.git
cd filar
cargo build --release
```

| Платформа | Бинарник |
|-----------|----------|
| Windows | `target\release\filar.exe` |
| macOS | `target/release/filar` |

**1.0.0** официально поддерживает Windows и macOS; Linux — не цель релиза
(пути данных через XDG уже есть в движке).

## 2. Конфигурация

У filar три места хранения настроек. Обычному пользователю ничего знать
о них не нужно — GUI-лаунчер всё делает автоматически. Этот раздел — для
тех, кто запускает через CLI или хочет вручную настроить профили.

### 2.1. Как это работает (обзор)

| Файл | Где | Кто пишет | Зачем |
|------|-----|-----------|-------|
| `settings.json` | `{OS data dir}/filar/` | GUI-лаунчер | Сохраняет состояние UI (SSH-профили, модель, URL, выбор) |
| `pending_launch.json` | `{OS data dir}/filar/` | GUI-лаунчер → TUI | Транзитный: передаёт настройки запуска от GUI к TUI, удаляется после чтения |
| `config.toml` | `{OS data dir}/filar/` | GUI-лаунчер (частично) + пользователь | Фолбэк для CLI-режима; полный набор настроек |
| OS Credential Manager / Keychain | Системное хранилище | GUI / TUI | API-ключи и SSH-пароли — **только здесь**, нигде в файлах |

Пути `{OS data dir}/filar/`:
- Windows: `%APPDATA%\filar\`
- macOS: `~/Library/Application Support/filar/`
- Linux: `~/.local/share/filar/` (или `$XDG_DATA_HOME/filar/`; не цель 1.0.0)

**Поток при запуске через GUI:**
1. Пользователь редактирует поля в лаунчере → сохраняются в `settings.json`
2. Нажатие «Launch» → пишется `pending_launch.json` + обновляется `[llm]` в `config.toml`
3. GUI запускает TUI-подпроцесс
4. TUI читает `pending_launch.json`, удаляет его, использует настройки оттуда

**Поток при запуске через CLI (без GUI):**
1. `pending_launch.json` не существует → TUI читает `config.toml`
2. Ключи берутся из env-переменных (или Credential Manager, если ранее сохранялись)

### 2.2. config.toml — справочник

```toml
# ── Режим подтверждения команд ─────────────────────────────
confirm_mode = "allowlist"
#   always    — каждая команда требует явного approve/deny
#   allowlist — read-only (ls, cat, ps...) выполняются автоматически; остальные — с подтверждением (по умолчанию)
#   never     — все команды без подтверждения (опасно!)
#   explain   — safe mode: агент обязан пояснить каждую команду и ждать подтверждения.
#               Сессия автоматически пишется в Markdown. Переключается клавишей F2.
#               (!command — shell escape — не затрагивается, работает как обычно.)

# ── Политики на тегах хостов (только ужесточение) ──────────
# Политика привязывается к тегу из tags = [...] у [[ssh_targets]].
# Для активного хоста с совпавшим тегом эффективный режим — самый строгий
# из: режима вкладки (F2), глобального confirm_mode и всех совпавших
# политик. Тег не может ослабить confirm_mode, только ужесточить; хосты
# без совпавших политик не затрагиваются (см. 2.3).
[[tag_policies]]
tag = "prod"
confirm_mode = "always"

# ── Группы хостов ──────────────────────────────────────────
# Именованный набор по тегам: хост входит в группу, только если несёт
# ВСЕ теги из match. Пустое правило не выбирает никого (не «весь парк»).
# Группа несёт политику (пока только read-only), лимит параллелизма,
# дедлайн на хост и необязательный LLM-профиль. Политика read-only
# обеспечивается транспортом: команды вне встроенного списка читающих
# отклоняются до отправки на хост. Состав виден в лаунчере на вкладке
# Groups при правке правила (см. 3.3).
[[host_groups]]
name = "Рабочий прод"
match = ["work", "prod"]
policy = "read-only"          # единственное значение в этой версии
max_parallel = 3              # по умолчанию 3
per_host_timeout_secs = 30    # по умолчанию 30
# llm_profile = "deepseek"    # необязательно; имя из [[llm_profiles]]

# ── LLM по умолчанию (профиль "default") ──────────────────
[llm]
model = "glm-5.1"
api_base_url = "https://open.bigmodel.cn/api/paas/v4"
max_tokens = 4096
# compact_at_tokens = 200000 # порог сжатия истории; 0 — отключить (см. 4.6)
# temperature = 0.3          # опционально (0.0–2.0)
# top_p = 0.9               # опционально (0.0–1.0]
# [llm.extra_body]           # опционально, произвольные поля в тело запроса
# thinking = { type = "disabled" }

# ── Дополнительные LLM-профили ─────────────────────────────
# Каждый профиль может использовать другую модель/провайдера.
# Ключи хранятся в Credential Manager под именем из key_env.
# compact_at_tokens задаётся отдельно для каждого профиля, потому что окна
# контекста у моделей разные (см. 4.6).
[[llm_profiles]]
name = "deepseek"
model = "deepseek-chat"
api_base_url = "https://api.deepseek.com/v1"
max_tokens = 8192
key_env = "DEEPSEEK_API_KEY"

# ── Таймауты (в секундах) ──────────────────────────────────
[timeouts]
command_secs = 300   # выполнение одной команды
llm_secs = 60        # один вызов LLM API
connect_secs = 15    # установка SSH-соединения

# Долгие jobs (pull/download/build): используйте инструменты
# start_background_job / background_job_status / cancel_background_job —
# не делайте `sleep N` под command_secs; для live-прогресса — Ctrl+T.

# ── SSH-таргеты ───────────────────────────────────────────
# Лаунчер синхронизирует свои SSH-профили в эту секцию при каждом Launch.
# Можно также добавлять таргеты вручную — лаунчер сохранит чужие записи.
[[ssh_targets]]
name = "my-server"
host = "192.168.1.100"
port = 22
user = "admin"
# tags = ["prod", "web"]   # свободные метки хоста; видны в статусной строке
#                          # TUI как `host [prod,web]`. В лаунчере — поле
#                          # Tags (через запятую).

[ssh_targets.auth]
type = "agent"        # agent | key | password
# path = "~/.ssh/id_ed25519"  # только для type = "key"
# password = "..."            # только для type = "password" (лучше SSH_PASSWORD env)

# ── Директория сохранения расшифровок ─────────────────────
# Куда Ctrl+S и авто-расшифровка (Explain mode) пишут .md файлы.
# Файлы раскладываются по подпапкам: <save_dir>/<имя таргета>/,
# локальные сессии — <save_dir>/local/ (см. 6.4).
# Не задано = текущая рабочая директория.
# save_dir = "C:\\Users\\me\\Documents\\filar-transcripts"

# Ранбук рядом с экспортом Ctrl+S (см. 6.4). true по умолчанию;
# false — Ctrl+S пишет только расшифровку, без обращения к модели.
# save_runbook = true
```

### 2.3. Режимы подтверждения

| Режим | Поведение |
|-------|----------|
| `always` | Каждая команда требует явного approve/deny |
| `allowlist` | Read-only (ls, cat, ps...) выполняются автоматически; остальные — с подтверждением (по умолчанию) |
| `never` | Все команды без подтверждения (опасно!) |
| `explain` | Safe mode: агент обязан пояснить каждую команду и ждать подтверждения. Сессия пишется в Markdown. Переключается F2 на лету. |

Политики на тегах (`[[tag_policies]]`) ужесточают режим для конкретных
хостов: работая на тест-хосте в `allowlist`, при переключении `Ctrl+O` на
хост с тегом `prod` режим автоматически поднимается до `always` — и
возвращается обратно при переключении назад. Политика никогда не ослабляет
режим: если глобальный `confirm_mode` строже политики — побеждает глобальный;
если тегов/политик несколько — побеждает строжайшая. Эффективный режим
виден в статусной строке справа.

### 2.4. API-ключи и пароли

**В GUI-режиме:** ввести ключ прямо в интерфейсе. Сохраняется в OS credential
store автоматически при первом Launch:

| Платформа | Хранилище | Service / ключи |
|-----------|-----------|-----------------|
| Windows | Credential Manager | service `filar` |
| macOS | Keychain | service `filar`; SSH — `ssh_target:{alias\|SSHn}` |

**В CLI-режиме:** через переменные окружения:

```bash
export GLM_API_KEY="ваш-ключ"          # профиль по умолчанию
export DEEPSEEK_API_KEY="ваш-ключ"    # именованный профиль
export SSH_PASSWORD="пароль-ssh"     # SSH auth type = "password"
# Windows PowerShell: $env:GLM_API_KEY = "…"
```

Ключи **никогда** не записываются в `config.toml`, `settings.json`, или
`pending_launch.json`.

### 2.5. Где искать config.toml

Поиск в порядке приоритета:
1. `FILAR_CONFIG` env (явный путь)
2. `./config.toml` (текущая директория)
3. `{OS data dir}/filar/config.toml` (сюда пишет лаунчер; см. §2.1)
4. `config.toml` рядом с исполняемым файлом (`filar.exe` / `filar`)

Если ни одного файла нет — используются встроенные значения по умолчанию.
Лаунчер при нажатии **Launch** всегда пишет свою секцию в
`{OS data dir}/filar/config.toml`, даже если читает файл выше по списку
(например, локальный `./config.toml`): файл-переопределение он не трогает
(см. 3.3 про группы).

### 2.6. Каталог флот-проверок (`fleet_checks.toml`)

Флот-проверка — это именованное описание одного read-only вопроса, который
задаётся сразу всей группе хостов. Модель **не сочиняет** такие команды: она
выбирает из каталога, а что лежит в каталоге — решает человек.

Каталог состоит из двух слоёв:

1. **Встроенный набор** вшит в бинарник (`include_str!`). Он работает на
   машине, где нет ни одного конфигурационного файла, и ничего ниоткуда не
   скачивает. Сейчас в нём шесть проверок:

   | Имя | Что спрашивает |
   |---|---|
   | `disk-usage` | размеры и заполненность файловых систем |
   | `block-devices` | блочные устройства, их размеры, типы и точки монтирования |
   | `processes` | запущенные процессы по владельцу и имени исполняемого файла |
   | `listening-sockets` | слушающие сокеты по протоколу и локальному адресу |
   | `kernel-version` | версия работающего ядра |
   | `os-release` | как хост сам себя называет (`/etc/os-release`) |

2. **Пользовательский набор** — файл `fleet_checks.toml` **рядом с
   `config.toml`** (тот самый файл, который выиграл поиск из 2.5). Его записи
   **дополняют** встроенные. Путь можно задать явно переменной окружения
   `FILAR_FLEET_CHECKS`. Если файла нет — это не ошибка, работают встроенные
   проверки.

Формат записи:

```toml
[[check]]
name = "sshd-config"                      # обязательное; [a-z0-9-_.], до 64 байт, уникальное
description = "Effective sshd configuration"  # обязательное, одна строка
command = "cat /etc/ssh/sshd_config"      # обязательное; строка или таблица вариантов
# preprocessor = "df"                     # необязательное: имя разборщика вывода
# compare = ["mount", "size"]             # колонки, по которым сравниваются хосты
```

#### Варианты команды под разные ОС

В реальном парке ОС разные — это норма, а не исключение. Команда, валидная на
Debian, падает на Alma. Поэтому `command` — это либо **одна строка** (она
выполняется везде), либо **таблица вариантов** по семействам ОС:

```toml
[[check]]
name = "disk-usage"
description = "Filesystem sizes and utilisation"
command = { default = "df --output=source,size,used,avail,pcent,target", alpine = "df" }
preprocessor = "df"
compare = ["mount", "filesystem", "size"]
```

Ключи: `debian`, `rhel`, `alpine` и необязательный `default` для всех
остальных. Опечатка в ключе (`alpine3`) — ошибка с явным сообщением, а не
молча проигнорированная строка: иначе проверка тихо перестала бы применяться
к Alpine, а ровно это варианты и должны предотвращать.

Именно так устроена встроенная `disk-usage`: GNU `df` принимает
`--output=`, а busybox-овый `df` на Alpine этот флаг отвергает. Обе формы
печатают одни и те же шесть колонок, поэтому таблица для сравнения выходит
одинаковая.

**Семейство ОС** определяется по `/etc/os-release` (`ID`, затем `ID_LIKE`)
один раз за сессию и кэшируется — производные вроде Alma, Rocky и Oracle
попадают в `rhel` автоматически. Хост, который не удалось отнести ни к
одному семейству, считается `unknown`: он получает `default`-команду, если
она есть.

#### Неприменимо — это состояние, а не ошибка

Если у проверки нет варианта под обнаруженное семейство и нет `default`, она
помечается **неприменимой** к этому хосту. Это отдельное состояние в
результате: хост не считается упавшим и не пропускается молча — в сводке
будет видно, что вопрос к нему просто не относится.

```toml
[[check]]
name = "debian-only"
description = "Имеет смысл только на Debian"
command = { debian = "cat /etc/debian_version" }
# на RHEL, Alpine и неопознанных хостах — «неприменимо»
```

`preprocessor` и `compare` идут только вместе (независимо от того, один у
команды вариант или несколько):

- **есть `preprocessor`** — вывод разбирается в таблицу, и `compare` обязан
  назвать хотя бы одну её колонку (иначе разбор некому использовать);
- **нет `preprocessor`** — сравнивается весь вывод целиком, и `compare`
  должен быть пустым (колонок просто нет).

#### Ошибка в одной записи не ломает остальные

Битая запись отбрасывается с объяснением, всё остальное продолжает работать.
Опечатка в ключе — тоже ошибка, а не молча проигнорированная строка. Причины
пишутся в лог при старте (`{OS data dir}/filar/logs`):

```text
WARN filar: fleet check rejected: check #2 ('broken-one') in /.../fleet_checks.toml:
     missing field `command`
WARN filar: fleet check rejected: check #4 ('typo-key') in /.../fleet_checks.toml:
     unknown field `preprocesor`, expected one of `name`, `description`,
     `command`, `preprocessor`, `compare`
```

Файл, который целиком не является валидным TOML, отбрасывается целиком —
встроенные проверки при этом остаются на месте.

Имя из встроенного набора переиспользовать нельзя: пользовательская запись
с именем `disk-usage` будет отклонена, а не подменит встроенную. Каталог, в
котором одно имя значит на двух машинах разное, хуже каталога, который прямо
об этом говорит.

#### Почему руками редактируемый файл — это не дыра

Команда из описания всё равно идёт через транспортный гейт read-only
(см. 3.3): список читающих команд вшит в код и не расширяется ни конфигом,
ни каталогом, ни моделью. Вписать в проверку `rm -rf /var/log` можно —
**выполнить нельзя**: гейт отклонит её до отправки на хост, и `;`/`&&` не
помогут. Редактируемость каталога даёт выразительность, а не права.

По этой же причине встроенный набор пока не использует разборщики для
`dpkg`/`rpm`/`systemctl`/`journalctl`/`ip`: эти бинарники сознательно не
входят в read-only allowlist, а расширять границу безопасности ради удобства
каталога — неправильный размен.

> Выбор проверок в интерфейсе и запуск по группе появятся вместе с
> флот-режимом (2.0): сейчас каталог загружается и валидируется при старте,
> но UI для него ещё нет.

## 3. GUI-лаунчер

При запуске без аргументов открывается окно "Filar — Launcher":

```text
┌──────────────────────────────────────────┐
│  Filar                                    │
│  Terminal with an AI agent over SSH       │
│──────────────────────────────────────────│
│  Recent sessions:                         │
│    + Start new session                    │
│    2025-06-20 14:30 | local | Помог…      │
│    2025-06-19 10:15 | my-server | …       │
│──────────────────────────────────────────│
│  Target:              [local        ▼]   │
│  LLM profile (preset): [default    ▼]    │
│  Model:               [glm-5.1        ]   │
│  API base URL:        [https://open.big… ]│
│  API key:             [··············]    │
│──────────────────────────────────────────│
│          [Launch]  [Cancel]              │
└──────────────────────────────────────────┘
```

- **Recent sessions** — список до 10 последних сессий (клик восстанавливает)
- **Target** — `local` или SSH-таргет из конфига
- **LLM profile (preset)** — пресет из конфига; при выборе автозаполняет поля Model и URL
- **Model** — имя модели (можно править вручную)
- **API base URL** — адрес API (можно править вручную)
- **API key** — ваш ключ к LLM API (вводится прямо в интерфейсе)
- **Launch** — запускает TUI с выбранными параметрами

### 3.1. Импорт списка хостов

Кнопка **Import…** рядом с «+ Add host» загружает парк хостов одним файлом —
адреса, порты, пользователи и теги. Секреты не импортируются: пароль
запрашивается при первом подключении и сохраняется в хранилище ОС, как обычно.

Формат выбирается по расширению файла:

- **TOML** (`.toml`) — та же форма, что в `config.toml`:

  ```toml
  [[ssh_targets]]
  name = "web-01"          # обязательное имя (alias)
  host = "192.0.2.10"      # обязательный адрес
  port = 22                # необязательно, по умолчанию 22
  user = "deploy"          # необязательно
  tags = ["prod", "web"]   # необязательно
  auth = { type = "password" }  # необязательно: password | key
  ```

  Посторонние секции и ключи игнорируются — импортировать можно готовый
  `config.toml` целиком. Поле `auth` задаёт тип аутентификации (подробнее —
  в 3.2); вложенные в него `password` и `path` не читаются — секреты
  остаются только в хранилище ОС.

- **CSV** (`.csv`) — для выгрузок из чужих инвентарей. Строка заголовка с
  колонками `name` и `host` (обязательные) и `port`, `user`, `tags`
  (необязательные); порядок колонок любой, регистр не важен, теги внутри
  поля — через `;`. Поддерживаются кавычки, переводы строк CRLF и BOM.

Если имя уже занято, лаунчер не решает молча: откроется диалог со списком
конфликтов и общим выбором для всех — **Skip** (пропустить), **Overwrite**
(перезаписать адрес/порт/пользователя/теги; сохранённый пароль остаётся,
только если адрес, порт и пользователь не изменились — иначе пароль
сбрасывается и его запись удаляется из хранилища при запуске),
**Rename** (добавить под первым свободным именем `имя-2`, `имя-3`, …) или
**Cancel import**. Битый файл список не меняет — внизу появится красная
ошибка с причиной (для CSV — с номером строки).

Результат импорта виден под списком хостов, например:
`Import: 20 added, 0 overwritten, 0 renamed, 0 skipped`.

### 3.2. Экспорт списка хостов

Кнопка **Export…** рядом с «Import…» сохраняет текущий список хостов в
TOML-файл того же формата, который читает импорт, — адреса, порты,
пользователи, теги и тип аутентификации. Секреты в файл **не попадают**:
ни паролей, ни ключей, ни путей к ним — файл можно коммитить в git и
передавать команде.

- Тип аутентификации каждой записи — `auth = { type = "password" }` (у
  хоста включена галочка «Save password») или `type = "key"`; при импорте
  в новый список тип восстанавливается.
- Пустые строки-заготовки в списке пропускаются.
- Результат виден под списком хостов: `Export: 5 hosts → D:\fleet.toml`.

Файл, записанный через **Export…**, читается обратно через **Import…**
без потерь: адреса, порты, пользователи, теги и тип аутентификации
восстанавливаются.

### 3.3. Группы хостов

Вкладка **Groups** рядом с **Hosts** задаёт группы хостов — именованные
наборы по тегам. Хост входит в группу, только если несёт **все** теги из
правила: `work, prod` выберет лишь хосты с обоими тегами одновременно.

- **Name** — имя группы; **Match tags** — теги через запятую; **Policy**,
  **Max parallel**, **Per-host timeout (s)** и **LLM profile** — параметры,
  которые группа несёт с собой. Политика `read-only` уже действует:
  в сессии на таком хосте транспорт пропускает только команды из
  встроенного списка читающих команд (зашит в код и не расширяется —
  ни конфигом, ни моделью), а запись отклоняется **до отправки на хост**:
  ни `;` с `&&`, ни подстановки не помогают обойти запрет — гейт вообще
  принимает только литеральный текст (без `$`/`${…}`, кавычек,
  экранирования, фигурных и glob-скобок), а флаги записи
  `sort`/`date`/`file` отклоняются и в формах `-oFILE`, `-ro`, `--out=…`.
  Интерактивный терминал (Ctrl+T) — это прямой ввод пользователя, он
  вне гейта.
  Лимиты (`Max parallel`, `Per-host timeout`) и `LLM profile` пока
  сохраняются и показываются; их применение к запуску — следующий шаг
  (флот-режим 2.0).
- Под каждым правилом — живой предпросмотр: `Effective now: 2 host(s) —
  web-1, db-1`. Он пересчитывается прямо во время правки тегов на вкладке
  **Hosts** — радиус действия правила виден сразу, а не при первом запуске.
- Пустое правило и правило без совпадений показаны серым текстом — это не
  ошибка. Пустое правило не выбирает никого: незавершённое определение
  никогда не означает «весь парк».
- Группы хранятся в `config.toml` в секции `[[host_groups]]` (см. 2.2) и
  записываются при нажатии **Launch**; пустые строки-заготовки не
  сохраняются. Имя группы обязательно и не должно повторяться — иначе
  Launch покажет ошибку.
- Лаунчер **читает** `./config.toml` раньше каталога данных ОС (порядок из
  2.5), а **записывает** группы при нажатии **Launch** — всегда в
  `{каталог данных ОС}/filar/config.toml`. Если запускать из каталога, где
  лежит свой `config.toml` с `[[host_groups]]`, правки вкладки Groups уйдут
  в файл каталога данных, а следующий запуск из этого каталога снова
  прочитает локальный файл — правки будут выглядеть потерянными. Лечится
  удалением (или ручной правкой) локального `config.toml` в каталоге запуска.

## 4. TUI — Режим агента

Основной режим работы. Вы пишете задачу на естественном языке, агент
выполняет команды и возвращает результат.

### 4.1. Горячие клавиши

Все шорткаты с модификатором используют **Ctrl** (Control), не ⌘ Command —
так на Windows, Linux и macOS. На macOS клавиша F1 часто требует **Fn+F1**
(см. `docs/PLATFORM_NOTES.md` → macOS shortcuts).

| Клавиша | Действие |
|---------|----------|
| `F1` | Оверлей справки (все горячие клавиши, по секциям); на macOS — часто Fn+F1 |
| `F2` | Переключить safe mode (Explain): агент обосновывает каждую команду, сессия пишется в Markdown автоматически |
| `Enter` | Отправить сообщение / Подтвердить выбранную кнопку |
| `Ctrl+Q` | Выход (в Confirming — сначала отклоняет) |
| `Ctrl+Z` | Отмена: прервать агента (Thinking) / отклонить команду (Confirming); во время сжатия истории отменяет и сам запрос сводки |
| `Ctrl+C` | Ничего (оставлен под копирование выделения) |
| `Ctrl+T` | Переключение между агентом и терминалом |
| `Ctrl+Tab` / `Ctrl+Shift+Tab` | Переключение вкладок |
| `Ctrl+N` | Новая вкладка (всегда local) |
| `Ctrl+W` | Закрыть вкладку (последняя → выход); во флоте — закрыть флот (см. 4.8) |
| `Ctrl+L` | Сменить LLM-профиль для текущей вкладки |
| `Ctrl+K` | Сжать историю сейчас (свернуть ранние ходы в сводку) |
| `Ctrl+O` | Оверлей выбора хоста (local + [[ssh_targets]]); группа из `[[host_groups]]` открывает флот; во флоте — открыть хост флота новой вкладкой (см. 4.8) |
| `Ctrl+J` | Боковая панель фоновых операций (см. 4.7); `Esc` — закрыть, `Up/Down` — выбор |
| `Ctrl+V` | Вставка из буфера обмена |
| `Ctrl+P` | Ввод пароля (маскированный) |
| `Up/Down` | Навигация по истории ввода (переживает перезапуск) |
| `!command` | Shell escape (прямой вызов команды) |
| `a` / `y` | Подтвердить команду |
| `d` / `n` | Отклонить команду |
| `Tab` | Переключение Approve/Deny в диалоге |

### 4.2. Управление мышью

| Действие        | Результат                                  |
|-----------------|--------------------------------------------|
| Колесо вверх/вниз | Прокрутка истории чата (по 3 строки)    |
| Клик по `▾`/`▸` | Развернуть/свернуть вывод команды          |
| Клик по заголовку команды | Развернуть/свернуть вывод        |
| Клик по `↓ N new` | Прокрутка к последним сообщениям         |
| Drag (зажать ЛКМ и тянуть) | Выделение текста и копирование в буфер |
| Двойной клик    | Выделение слова                            |
| Тройной клик    | Выделение строки                           |

В режиме подтверждения команды:
- Клик по кнопке **Approve** / **Deny** — выбирает действие
- `Enter` активирует выделенную кнопку (по умолчанию — **Deny**)

В интерактивном терминале (Ctrl+T):
- Колесо — скролл истории терминала (или стрелки в less/man)
- Клик/перетаскивание — проброс мыши в приложение (vim, htop, mc)

### 4.3. Режимы приложения

- **Normal** (поле ввода) — ввод текста, отправка агенту
- **Thinking** (агент работает) — ожидание ответа LLM / выполнения команд
- **Confirming** (подтверждение) — агент просит разрешение на команду
- **Interactive** (терминал) — обычный эмулятор терминала

### 4.4. Блоки чата

Каждое сообщение отображается цветным блоком:

| Цвет     | Тип       | Описание                              |
|----------|-----------|---------------------------------------|
| Cyan     | User      | Ваше сообщение                        |
| Green    | Agent     | Ответ/рассуждение агента              |
| Yellow   | Command   | Команда + вывод + статус (✓/✗)       |
| Red      | Error     | Сообщение об ошибке                   |
| Gray     | System    | Системное уведомление                 |
| Gray     | Summary   | Сводка свёрнутой части истории (см. 4.6) |

### 4.5. Подтверждение команд

Когда агент предлагает выполнить команду, вы видите:

```
⚠ COMMAND CONFIRMATION REQUIRED
Agent wants to run:  sudo apt update
Explanation:         Updating package lists to check available versions
⚠ WARNING: This command may modify system state

[a]pprove  /  [d]eny
```

- Нажмите `a` или `y` — команда выполняется
- Нажмите `d` или `n` — команда отклоняется, агент продолжит работу
- `Ctrl+Z` — отклонить команду (без выхода)
- `Ctrl+Q` — отклонить команду и выйти из приложения

### 4.6. Сжатие истории

Длинный разговор рано или поздно упирается в окно контекста модели. Чтобы
сессию не приходилось начинать заново, filar **сворачивает начало истории в
сводку**, а последние ходы оставляет дословно.

**Когда срабатывает.** Порог задаётся параметром `compact_at_tokens` (по
умолчанию `200000`) и считается по количеству токенов, которое провайдер
сообщил для последнего запроса. Параметр задаётся отдельно для каждого
LLM-профиля, потому что окна контекста у моделей разные: цифра, разумная для
модели на 1M токенов, бессмысленна для модели на 128k. Ставьте её заметно ниже
реального окна — сжатию нужен запас, чтобы успеть сработать. Значение `0`
отключает автоматическое сжатие.

**Что вы видите.** Ничего не происходит молча. В ленте появляется строка перед
сжатием («compacting the first N blocks») и после («N blocks to M»), а сама
сводка остаётся в ленте отдельным блоком типа `Summary` — его можно развернуть
и прочитать, чтобы проверить, что именно модель запомнила.

Сводку просят сохранить, по порядку: уже выполненные команды и их результат,
установленные факты о системе, текущую гипотезу и незакрытые вопросы.

**Ручной запуск — `Ctrl+K`.** Сворачивает историю по вашей инициативе, не дожидаясь
порога. Удобно перед переходом к новому этапу работы. `compact_at_tokens`
при этом игнорируется, так что `Ctrl+K` работает и при отключённом автосжатии.

**Сжимается контекст, а не запись.** Свёрнутые ходы остаются и в сессии, и в
расшифровке: `.md`, который пишется при выходе, экспорт по `Ctrl+S` и
сохранённая сессия после переоткрытия содержат все ходы целиком, а сводка
показана в том месте, где произошла свёртка. То, что несёт с собой модель, и
то, что вы можете перечитать, — намеренно разные вещи.

**Стоимость.** Запрос на сводку оплачивается как любой другой и попадает в
счётчики токенов и стоимости сессии, а также в разбивку по профилям. Сессия,
сжимавшаяся несколько раз, покажет, во что это обошлось.

**Если сводка не удалась.** История остаётся нетронутой, а ваш ход всё равно
уходит на полной истории — лента об этом сообщит. Неудачное сжатие не стоит вам
хода.

**Отмена — `Ctrl+Z`.** Нажатая во время сжатия, отменяет сам запрос сводки, а не
только ожидание: работа прекращается сразу, история не меняется, и в счётчики
сессии ничего не записывается. Успел ли провайдер начать обработку запроса и
списать за неё — от filar уже не зависит; отмена гарантирует, что ответа никто
не ждёт и в вашу статистику он не попадёт. Сессия продолжает работать как
обычно.

### 4.7. Боковая панель: фоновые операции

Когда агент запускает долгую команду фоном (`start_background_job` —
`tail -f`, сборка, бэкап), она видна в боковой панели справа от ленты.
Панель показывает дерево **«операция → хосты»**: строка операции (id и
команда), под ней — хосты, на которых она идёт. Фоновая задача на одной
вкладке — операция из одного хоста; флот-операции лягут в то же дерево.
Внизу панели — хвост вывода выбранного хоста.

- **Статусы символом и словом**, не только цветом: `▸` работает, `✓` готово,
  `✗` упало (с кодом выхода), `■` отменено. В ASCII-режиме (conhost) —
  `>`, `+`, `!`, `~`.
- **Счётчик в статус-баре** — `ops ▸2 ✓1`: виден при закрытой панели и на
  любой вкладке, так что задача не теряется при переключении.
- **Ширина терминала от 120 колонок** — панель пристыкована постоянно, пока
  есть хоть одна операция, и лента сужается под неё. **Меньше 120 колонок** (в
  том числе 80) лента остаётся во всю ширину, а панель выезжает поверх неё
  по `Ctrl+J` и убирается по `Esc`.
- `Ctrl+J` передаёт фокус панели: `Up/Down` выбирают операцию или хост,
  `Esc` закрывает. Остальные клавиши идут в поле ввода — печатать можно, не
  закрывая панель. В интерактивном терминале (`Ctrl+T`) `Ctrl+J` уходит в
  удалённый шелл, как и прочие клавиши.
- Панель показывает задачи **открытых** вкладок; задача закрытой вкладки из
  панели пропадает.

**Свежесть статуса.** Локальная задача обновляется в реальном времени
(вывод и завершение — раз в полсекунды, пока задача идёт). Статус задачи на
удалённом хосте — на момент последнего опроса агентом
(`background_job_status`), и панель так и пишет: `running (as of last poll)`.
Сама панель на хост ничего не отправляет: опрос — это команда на удалённой
машине, и она идёт только через агента и гейт подтверждения.

**Отмены с панели нет.** Отменить задачу может агент
(`cancel_background_job`, через гейт подтверждения — как любая команда на
хосте). Отмена своей же задачи — это тоже `kill` на удалённой машине, и
исключения из гейта для неё не делается.


### 4.8. Флот: слой над вкладками

Флот — это одна сессия диалога над **группой хостов** из `[[host_groups]]`
(см. 3.3). Это не вкладка в общем ряду, а отдельный слой поверх вкладок:
обычные вкладки при входе и выходе остаются как были, а одиночный режим
ничем не меняется.

- **Вход.** На старте — `filar --group <имя>`, по ходу работы — `Ctrl+O`:
  в конце списка идёт секция `groups — fleet` с группами, у каждой указано
  число хостов и её правило (`#web #prod`). Флот показан первой меткой в
  полосе вкладок: `[fleet: web-prod (2)]`.
- **Состав фиксируется при входе.** Хосты выбираются по правилу группы один
  раз. Перетегировать хост после входа — состав открытого флота не меняется.
- **Выход.** `Ctrl+W` закрывает флот и возвращает на вкладку, с которой в
  него вошли. `Ctrl+Tab` / `Ctrl+1…9` уходят на вкладки, оставляя флот
  открытым в фоне; снова выбрать ту же группу в `Ctrl+O` — вернуться в него
  (тот же состав, не новое открытие). Другая группа заменяет открытый флот:
  флот один.
- **`Ctrl+N` во флоте** создаёт обычную вкладку, а не второй флот. Номера
  вкладок считают только обычные вкладки.
- **`Ctrl+O` во флоте — провалиться в хост.** Оверлей показывает только хосты
  флота (без `local` и чужих таргетов). Выбранный хост открывается **новой
  обычной вкладкой** со своим подключением; флот остаётся открытым. Сценарий:
  «вижу, что проблема на web-3, — иду туда один на один». Хост может быть
  одновременно во флоте и во вкладке (и даже в двух вкладках) — у каждой
  вкладки своё подключение, флоту своё не нужно. Строка группы в том же
  оверлее по-прежнему переключает флот.

**Чего флот пока не умеет.** Запуск агента по группе ещё не подключён:
сообщение во флоте **никуда не отправляется** (остаётся в поле ввода), и у
флот-сессии нет своего транспорта. Одноадресные возможности — терминал
(`Ctrl+T`), `!команда`, ввод пароля (`Ctrl+P`), выбор пути (`/`,
`Ctrl+Shift+F/D`), восстановление сессии (`F3`) — во флоте отказывают с
пояснением и ничего не выполняют.

## 5. TUI — Интерактивный терминал

Нажмите `Ctrl+T` в режиме агента для переключения в обычный терминал.

```
┌──────────────────────────────────────────┐
│ INTERACTIVE                    local     │ ← статус-бар
│──────────────────────────────────────────│
│ user@machine:~$ ls                       │
│ Documents  Downloads  Music  Pictures    │
│ user@machine:~$ _                        │ ← курсор
│──────────────────────────────────────────│
│ Ctrl+T=Agent mode │ (terminal input is forwarded) │ ← help-бар
└──────────────────────────────────────────┘
```

- Работает локальный PTY (команды выполняются на вашей машине)
- **Шелл:** на Unix/macOS — `$SHELL` (обычно `zsh` на Mac), иначе `sh`;
  на Windows — `cmd.exe`. Команды агента по-прежнему идут через отдельный
  non-interactive executor (`sh -c` / PowerShell) и не зависят от этого PTY
- Полная поддержка ANSI: `vim`, `htop`, `less`, `top` и т.д.
- Ресайз окна автоматически меняет размер терминала
- `Ctrl+T` — вернуться в режим агента (терминал остаётся живым в фоне)
- При выходе из шелла (exit/EOF) — автоматический возврат в режим агента
- **С 0.6.0:** у каждой вкладки свой терминал. Запустили долгую команду —
  переключились на другую вкладку `Ctrl+Tab`, вернулись — всё на месте.
  Закрытие вкладки `Ctrl+W` закрывает её терминал.
- Ярлыки вкладок показывают маркеры активности: `●` — агент работает,
  `?` — ожидает подтверждения, `○` — новый вывод в фоновой вкладке

## 6. Сессии

### 6.1. Автосохранение

Каждая сессия **автоматически сохраняется** при выходе из TUI (Ctrl+Q или
закрытие терминала).

Сохраняется:
- ID сессии (Unix timestamp)
- Timestamp (дата и время)
- Имя таргета (local / SSH-таргет)
- Имя LLM-профиля
- Все сообщения чата (включая вывод команд)
- Ходы, свёрнутые сжатием истории (см. 4.6) — они хранятся отдельно от
  текущего контекста, поэтому переоткрытая сессия не теряет начало разговора

### 6.2. Хранилище

- **Windows:** `%APPDATA%\filar\sessions\`
- **macOS:** `~/Library/Application Support/filar/sessions/`
- **Linux:** `~/.local/share/filar/sessions/`

Формат: JSON-файлы (`<id>.json`). Хранится не более **10 последних** сессий
(старые удаляются автоматически).

### 6.3. Восстановление

**Через GUI:** кликнуть на сессию в списке "Recent sessions" → Launch.

**Через CLI:**
```powershell
filar.exe --target local --session 1718900000
```

При восстановлении загружается вся история чата. В начале добавляется
системное сообщение: "Session restored — history loaded from disk".

### 6.4. Экспорт в Markdown (Ctrl+S)

`Ctrl+S` сохраняет всю переписку текущей вкладки в `.md`-файл — включая ходы,
свёрнутые сжатием истории (см. 4.6). Файлы пишутся в `save_dir` из
`config.toml` (не задан — текущая рабочая директория), внутри — **отдельная
папка на каждый таргет**. Имя папки — алиас таргета (если алиаса нет — `SSHn`),
приведённый к безопасному виду: посторонние символы заменяются на `-`,
зарезервированные имена Windows (`CON`, `COM1`, `LPT9`, …) получают `_` перед
расширением, хвостовые точки и пробелы отбрасываются, пустой результат
становится `target`:

```
<save_dir>/
  prod-web/
    prod-web.disk-full.2026-09-10.2139.md
  db-replica/
    db-replica.2026-09-10.2201.md
  local/
    local-1.2026-09-10.2210.md
```

Локальные вкладки складываются в `local/`. Папка создаётся при первом
сохранении в этот таргет; при совпадении имён появляется суффикс `-1`, `-2`, ….
Транскрипт Explain-режима (F2) создаётся в той же подпапке, в какой был
открыт, и остаётся там, даже если хост вкладки сменился.

**Ранбук рядом с экспортом.** При включённом `save_runbook` (по умолчанию;
отключается в `config.toml`) явный `Ctrl+S` кладёт рядом с расшифровкой второй
файл — `{имя}.runbook.md`: сессию, свёрнутую в обобщённую процедуру (симптом,
предусловия, шаги с разбором вывода, критерии «здорово/проблема», следующие
действия). Конкретные хосты, аккаунты и пути заменяются плейсхолдерами
(`<host>`, `<user>`, `<service>`); секреты в файл не попадают. Ранбук пишет
тот же профиль, что и у вкладки, расход токенов учитывается в счётчиках
сессии. Пока запрос идёт, оверлей показывает «Generating runbook...»;
`Ctrl+Z` прерывает его (расшифровка остаётся на диске), ошибка модели не
ломает сохранение — и то и другое видно в ленте. Сессия без выполненных
команд ранбук не получает. Автосохранение F2 и сохранение при выходе ранбук
никогда не пишут — только явный `Ctrl+S`.

## 7. Логи

Пока TUI активен, логи **не пишутся в терминал** (иначе строки лога легли бы
поверх интерфейса). Вместо этого весь лог идёт в файл, а сообщения уровня
**WARN и ERROR дополнительно дублируются в чат** как системные строки
(например, `filar_transport::ssh: reader: channel closed` при разрыве SSH).

### 7.1. Где лежит файл

- **Windows:** `%APPDATA%\filar\logs\filar.log`
- **macOS:** `~/Library/Application Support/filar/logs/filar.log`
- **Linux:** `~/.local/share/filar/logs/filar.log`

Файл ротируется посуточно (`filar.log.YYYY-MM-DD`). В нём — полная запись
с временными метками, включая уровни ниже WARN.

### 7.2. Уровень логирования

Уровень берётся из переменной окружения `RUST_LOG` (по умолчанию `info`).
Чтобы поднять детализацию:

```powershell
$env:RUST_LOG = "debug"
filar.exe
```

Можно фильтровать по модулю, например только транспорт:
`$env:RUST_LOG = "filar_transport=debug,info"`.

## 8. CLI-аргументы

```
Usage: filar [--target <name>] [--group <name>] [--llm <profile>] [--session <id>]

Options:
  --target <name>   Подключиться к таргету ('local' или имя SSH-таргета из конфига)
  --group <name>    Сразу открыть флот по группе из [[host_groups]] (см. 4.8)
  --llm <profile>   Использовать LLM-профиль ('default' или имя из [[llm_profiles]])
  --session <id>    Восстановить сессию по ID
  -h, --help        Показать справку
```

Без аргументов → GUI-лаунчер.

### Примеры

```powershell
# Локальная работа, LLM по умолчанию
filar --target local

# SSH на сервер, DeepSeek
filar --target my-server --llm deepseek

# Восстановить сессию на локальной машине
filar --target local --session 1718900000

# Флот по группе web-prod поверх локальной вкладки
filar --target local --group web-prod

# Только GUI (без аргументов)
filar
```

## 9. Типичный сценарий работы

### Сценарий 1: Диагностика через агента

1. Запустите: `filar --target my-server`
2. Введите: "Найди, какой процесс слушает порт 8080, и покажи его рабочую директорию"
3. Агент предложит: `sudo lsof -i :8080` → подтвердите (a)
4. Агент предложит: `ls -la /proc/<pid>/cwd` → подтвердите (a)
5. Агент выдаст итоговый ответ с путём

### Сценарий 2: Быстрый фикс через терминал

1. Запустите: `filar --target local`
2. Нажмите `Ctrl+T` — переключитесь в терминал
3. Выполните нужные команды вручную
4. Нажмите `Ctrl+T` — вернитесь к агенту
5. Спросите агента: "Проверь, что сервис nginx запущен"

### Сценарий 3: Восстановление вчерашней сессии

1. Запустите без аргументов: `filar`
2. В GUI выберите вчерашнюю сессию из списка
3. Нажмите Launch — история загрузится
4. Продолжите диалог: "А теперь проверь логи за сегодня"

## 10. Решение проблем

### "failed to load config"
- Filar работает и без `config.toml` — используются значения по умолчанию
- Для CLI-режима создайте `{OS data dir}/filar/config.toml` (см. раздел 2)
- Или укажите путь: `$env:FILAR_CONFIG = "C:\path\to\config.toml"`

### "API key is required"
- В GUI-режиме: введите ключ в поле "API key" и нажмите Launch
- В CLI-режиме: установите переменную `$env:GLM_API_KEY = "ваш-ключ"`

### "SSH target 'xxx' not found"
- Проверьте имя таргета в `config.toml` (поле `name` в `[[ssh_targets]]`)
- Список доступных таргетов смотрите в `config.toml` в секциях `[[ssh_targets]]`

### SSH-подключение не удаётся
- **Пароль:** установите `$env:SSH_PASSWORD`
- **Ключ:** проверьте путь в `config.toml` → `[ssh_targets.auth]` → `path`
- **Порт:** проверьте поле `port` (по умолчанию 22)

### TUI отображается некорректно
- Убедитесь, что терминал поддерживает ANSI (Windows Terminal, PowerShell 7)
- Минимальный размер окна: ~80×24

### Сессии не сохраняются
- Проверьте права на запись в `{OS data dir}/filar/sessions/`
- Создайте директорию вручную при необходимости

## 11. Безопасность

- **Ключи API** вводятся в GUI или через env-переменные, никогда не хранятся в config.toml
- **Режим `allowlist`** (по умолчанию): read-only команды выполняются автоматически,
  остальные требуют подтверждения
- **Режим `explain`** (safe mode, F2): агент обязан пояснить каждую команду,
  сессия пишется в Markdown автоматически
- **Деструктивные команды** (rm -rf, mkfs, dd...) помечаются предупреждением ⚠
- **Политика `read-only` групп хостов** обеспечивается транспортом: на
  таком хосте команды вне встроенного списка читающих отклоняются до
  отправки; гейт принимает только литеральный текст, так что запись не
  проходит ни через `;`, `&&`, ни через подстановки, кавычки,
  экранирование и глоб-символы (см. 3.3)
- **Zero-install:** на удалённой машине не создаётся никаких файлов —
  команды выполняются в существующем шелле через SSH-канал
